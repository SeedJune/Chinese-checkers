# 开发日志 · 2026-08-03

给 2 人对战接上第一个真正会下棋的 bot：minimax + α-β 剪枝，并在开始界面上把任意
一位玩家切成「电脑」。

上一篇日志第八节说 `agents/base.py` 的 `Agent` 协议和 `player_moves()` 就是 bot 的
接入点。事实证明确实如此——`core/` 这次一行没改。

## 一、先量，再选

选算法之前先把这个游戏的性质量出来（`Game.new(2)`，本机 Python 3.12）：

| 指标 | 实测 |
| --- | --- |
| 开局分支因子 | 14 |
| 中局分支因子 | 平均 51，最大 65 |
| `player_moves()` 全量着法生成 | 0.10 ms |
| `state.apply()` + `state.undo()` | 0.002 ms |

**分支因子远低于中国跳棋的一般印象。** 通常说跳棋分支因子上百，那是 6 人局
（60 颗子挤在 121 个孔里，连跳链又长又多）。2 人局只有 20 颗子，棋盘很稀，
连跳链短，分支因子跟国际象棋是一个量级。

这个数字直接决定了选型的可行域。写了个 60 行的 negamax+αβ 原型从中局位置实测：

| 深度 | 全宽度 | beam=16 |
| --- | --- | --- |
| 4 | 10 188 结点 / 0.30 s | 1 517 / 0.05 s |
| 5 | 238 942 结点 / 3.03 s | 10 413 / 0.32 s |
| 6 | 583 245 结点 / 19.5 s | ≈2 s |

1 秒预算能到深度 5–6。够了。

### 为什么是 α-β 而不是 MCTS

这是本次唯一需要认真论证的决定。

**决定性理由：这个局面有一个又便宜又准的评估函数。** 跳棋是纯赛跑——不吃子、
没有子力、没有战术地平线，唯一要紧的就是每颗子还要走多远。「所有棋子到目标营地尖的
立方距离之和」几乎单调对应胜负，而立方坐标下这个距离就是 `(|dx|+|dy|+|dz|)/2`，
连 BFS 预计算都不用（上一篇第八节已经指出这点）。α-β 正是把好评估函数兑现成棋力的
那个搜索。

**MCTS 在这里要跟三件事作对：**

1. 无吃子、无终局压力，**随机 rollout 几乎永不终止**——棋子会在星盘中央游荡上千步。
2. 要让它能用，必须给 rollout 加启发式策略 + 提前截断 + 用距离函数打分。
   那等于把 α-β 的评估函数原样搬进来，却换来更复杂的实现和更差的战术精度。
3. 分支因子 50 会稀释访问次数，而 α-β 在同样的分支因子下把有效分支压到 √b ≈ 7。

UCT 在跳棋上的已知优势场景是 **3 人以上**的多人局——那里 α-β 根本不适用。
2 人零和完全信息局面上，α-β 是**精确**的，没有近似误差。

被否掉的其他候选：纯贪心（留着当「简单」难度）；A\* 单智能体规划（跳棋交互弱，
其实不算差，但 α-β 深度 1 就覆盖了它）；max^n / paranoid（3–6 人局才需要，本次不做）。

## 二、评估函数

```
cost(p) = 1.0 · Σ distance(棋子, 目标营地尖)
        + 0.6 · max distance(...)
        + 2.0 · (自己目标营地里仍然空着的格子数)

evaluate(state, p) = cost(对手) − cost(p)
```

三个设计点，每个都是被规则逼出来的：

**距离取到营地尖，不是取到最近的营地格。** 尖是最深的那个洞，把所有子往尖上拉，
营地就会**从里往外填**——这正是 `home_lock`（进家不得出家）要求的填充顺序。
一颗子如果先停在营地口，它永远出不来给后面的子让路。用「到尖的距离」这一项
自动规避了这个陷阱，不需要额外写填充顺序逻辑。（营地内各格距尖 0–3，填满时该项恒为 20。）

**`max` 项**罚掉队的那一颗。赢需要**每个洞**都被填上，而距离和对「9 颗到家 + 1 颗
掉在半路」和「10 颗都在中途」给的分可能差不多。没有这一项，bot 会兴高采烈地把九颗子
送回家然后抛弃第十颗。

**空洞项**在开局恒为 0（目标营地被对手坐满），随对手撤离才升起，必须回到 0 才能赢——
它就是 `seat_is_home()` 的字面内容。它解决的是「对手赖在我方营地里」时距离和永远
压不到最小值、评估失灵的情况。

叶子先查 `has_finished()`，命中直接返回 ±WIN。这一项和空洞项都从
`player_terms()` 的同一次遍历里出来，因为它们走的是同一批营地格，而这个函数在每个
叶子上都跑。

## 三、搜索实现

`agents/minimax.py`。要点：

- **negamax + α-β**，用 `state.apply()` / `state.undo()` 走子回退而不是深拷贝。
  `undo` 已经是 `apply` 的精确逆操作，`apply` 又不做校验（着法来自 `player_moves`，
  天然合法），所以这条路径干净且几乎免费（0.002 ms）。
- **迭代加深** + 时间预算，超时返回上一层完成的最好着法。
- **着法排序**：置换表着法 → 杀手着法（每层 2 个）→ 按「向家推进了几格」降序。
  α-β 的收益几乎全在这里。
- **置换表**：Zobrist 哈希，固定种子（可复现）。**每个结点从头算哈希**，不做增量更新——
  20 颗子 20 次异或约 5 µs，只占结点成本 5%，而增量哈希在 undo 路径上极易写错且
  错了不会报错，只会悄悄下臭棋。
- **beam**：根节点**不剪**（bot 永远权衡它真正能走的每一步），根以下按排序取前 K 个。
- **重复局面规避**：agent 记住自己走进过的局面哈希，根节点对回到已见局面的着法扣 0.5 分，
  防止评估打平时来回蹭子。

三档难度是**同一个搜索的三组旋钮**，不是三个算法：

| 难度 | 配置 | 实测 |
| --- | --- | --- |
| 简单 | 深度 1，在最好的 2.0 分之内随机取 | < 1 ms |
| 普通 | 固定深度 3 | ≈ 50 ms |
| 困难 | 迭代加深，预算 1.0 s，beam 20 | ≈ 1 s，深度 5–6 |

## 四、遇到的两个真 bug

### 1. 超时不回退，把搜索局面留在树的深处

`_Timeout` 异常从递归深处抛出时，**一路上的 `state.undo()` 全被跳过了**。
异常传播出来后，搜索用的那份局面停在树里某个中间状态，紧接着
`select_move` 拿它 `apply(best)` 就 `KeyError`。

只有「困难」难度会触发（唯一带时间预算的档）。表现是自对弈跑到一半直接崩。

修法没有用 try/finally（每个结点都加代价）：`snapshot()` 交出来的局面 history 是空的，
所以**history 里剩下什么，就正好是搜索还欠着 undo 的那些着法**，捕获处
`while state.history: state.undo()` 一把清干净。O(深度)，每结点零开销，而且用的是
引擎自己保证的精确逆操作。

`test_running_out_of_time_leaves_the_search_copy_clean` 盯着这条。

### 2. 重绘重入，把电脑搭到一半的路线抹掉

`_play_bot_move` 先 `select` + `extend` 把路线搭出来，再 `board_view.refresh()`
把它画给人看一眼。但 `refresh()` → `on_state_changed(None)` → `_maybe_start_bot_turn()`，
而那时 `_bot_thinking` 已经被置回 False、回合还是电脑的——于是它**又启动了一次搜索**，
并且开头那句 `game.cancel()` 把刚搭好的路线清了。表现是电脑「思考完了但不走」，
状态栏显示「当前没有可以确认的走法」。

修法：`_bot_thinking` 的语义从「正在搜索」改成「电脑正在走这一回合」，
横跨搜索 + 亮路线 + 提交，只在 `confirm_move()` **返回之后**才落下——那时
`_animating` 已经接管了，重入的 `_maybe_start_bot_turn` 照样会早退。

这类 bug 的根源是 `_on_state_changed` 被设计成「任何重绘都会经过」。这个设计是对的
（谁都不用记得去启动 bot），代价就是从它出发的一切都必须幂等。

## 五、UI 接线

**菜单**：2 人局（经典 2 人 + 三色对战都满足）每个玩家行加一组「人类 / 电脑」选择片，
外加一行难度。选择片是手绘的扁平按钮而不是 `ttk.OptionMenu`——这个屏幕整个是手绘的，
放一个原生控件进去，它会是全场唯一穿着系统外壳的东西。

**线程**：搜索跑在工作线程上，通过 `queue.Queue` 把着法交回主线程轮询取。
不用从子线程调 `after`（Tkinter 不保证线程安全）。线程拿到的是
`agents.detached(game)` ——一份共享不可变元数据、复制局面、丢掉历史的副本，
所以它做什么都碰不到玩家正在看的那局。

**generation 计数器**：线程停不掉，那就不停——开新局 / 返回菜单 / 悔棋时把计数器加一，
旧搜索的结果回来时对不上号，直接丢弃。

**落子走人类完全相同的通道**（`select` → `extend` → `confirm_move`），
所以动画、横幅、名次面板、状态栏全部免费复用，UI 里没有一条 bot 专用路径。
落子前先把选好的路线画出来停 220 ms，这样这步棋是**可读的**，而不是「棋子忽然在别处了」。
另外给了 320 ms 的最短思考时间——「简单」难度不到 1 ms 就出手，瞬间落子读起来像卡帧。

**输入锁**：`BoardView.locked`，和既有的 `_animating` 一起折进 `_frozen`，
所有输入入口只问这一个谓词。唯一的例外是 `confirm_move()` ——它在 `locked` 时仍然开放，
因为那正是 app 用来落 bot 子的通道。

**悔棋退回自己的回合**：只退一手会把同一个回合还给电脑，它立刻重走一遍，
看起来就是「悔棋没反应」。所以一直退到轮至人类为止。这同时也是中断一个你不想再等的
电脑的办法——所以电脑思考时悔棋按钮**故意保持可用**，其余三个按钮全灰。

## 七、遗留

- **3–6 人局没有 bot**。α-β 只对两方成立，多人局要 max^n 或 paranoid，
  另开一轮。菜单在非 2 人局下直接不显示电脑选项，`MinimaxAgent` 内部也留了一条退化成
  深度 1 贪心的路径以防被别处调用。
- **自对弈的胜局常常只有 3–7 颗子到家**，不是 bug：随机对手把一堆子留在自己的出发营地
  （＝我方的目标营地）里没动，按「填满所有可用空位即判胜」的规则，我方填掉剩下的洞就赢了。
  这是上一篇第七节已经记下的规则字面推论。真人对手会把子挪走，所以这个现象只出现在
  对弱 bot 的自对弈里。
- **对称归一化没做**。上一篇提到棋盘在 6 旋转 + 2 镜像下不变，12 个等价局面可以归一到
  同一规范型，置换表能省一个数量级。但收益主要在开局，而且要把着法也跟着映射回去，
  复杂度不划算，先记在这里。
- 开局库、和棋 / 无进展判定、RL 都还没有。
